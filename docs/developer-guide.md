# Developer guide

## Setup

```bash
git clone https://github.com/Anurag-1205/DPDP-Audit.git && cd DPDP-Audit
git config user.name "<your GitHub username>" && git config user.email "<your email>"
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt && pip install -e ".[dev]"
cp .env.example .env          # add GEMINI_API_KEY only if you run B4
pytest -q                     # tests needing OPP-115 or the ladder are skipped until they exist
```

System requirements: Python ≥ 3.10, `pdftotext` (poppler-utils), and Docker if you run PoliCheck.
GPU work runs on Kaggle ([infrastructure.md](infrastructure.md)).

## Data formats

**Run (system output).** One JSON file per case and seed:

```json
{
  "case_id": "1028_v1", "system": "B2", "seed": 0, "model": "Qwen/Qwen2.5-7B-Instruct-AWQ",
  "findings": [{"flow_id": "f4", "data_type": "Computer information",
                "gap_type": "undisclosed_sharing", "level": "vague",
                "sections": ["Sec. 5(1)"], "evidence": "...", "uncertain": false}],
  "flow_labels": {"f1": {"label": "clear", "confidence": null}},
  "token_prob": 0.93, "usage": {"prompt": 2914, "output": 310}, "parse_error": null
}
```

- A failed model call is still saved, with `parse_error: "call failed: ..."`. `--redo-failed` re-runs
  it.
- The answer-key format is in [benchmark.md](benchmark.md#data-model).

## Conventions

- **IDs:**
  - systems are S1–S4, B1–B4, `full` and A1–A5;
  - specifications are SPEC-01 to SPEC-09 (`specs.md`);
  - research questions and hypotheses are RQ1–RQ4 and H1–H6.
- **Frozen artefacts:** do not edit or regenerate these without a team decision recorded in `specs.md`. Any change invalidates the
  stored runs.
  - `data/benchmark/main/`
  - `data/dpdp/gap_to_section.csv`
  - `data/tools/*mapping*.csv`
  - `gold_rules.py`
- **Determinism:** seeds are fixed (split 13, generator 0, LLM seeds 0–2). LLM replies are cached in
  `outputs/cache/llm/`, keyed by backend, model, prompt, seed and temperature.
- **Results:** anything that should be versioned is written under `results/`; scratch goes to
  `outputs/`, which is ignored as a whole.
- **No LLM in ground truth:** answer keys and ladder rungs come from scripts and templates, checked by
  people.
- **Style:** match the surrounding code; type hints on public functions; a module docstring stating
  the module's job; tests for every new module.

## Adding a new system under test

1. Implement it so that it returns the run format above, with `findings` and `flow_labels`.
2. Save outputs with `runs.save_run(split, system_id, seed, out)`.
3. Score with `python scripts/score_runs.py --systems <ID>`, which adds it to
   `results/scores/{split}.json`.
4. Add its row to the system tables in [evaluation.md](evaluation.md) and its spec in
   `specs.md`.

## Working together

- **Pull first:** run `git pull --rebase` before starting work.
- **One branch per task:** for example `spec-04-pipeline`. Merge to `main` when its tests pass.
- **Commits:** short imperative messages ("Add mismatch finder"), one logical change per commit, real
  dates, your own git identity.
- **Definition of done:**
  - code and tests pass;
  - results are committed under `results/`;
  - the spec's acceptance criteria are ticked with evidence;
  - the docs are updated.
